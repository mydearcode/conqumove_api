CONQUMOVE iOS AUTH + MOVEMENT + CABLE CONTRACT

1. Environment configuration

Development defaults:
- base_url: http://localhost:3000
- cable_url: http://localhost:3000/cable

Staging / production:
- Set CONQUMOVE_PUBLIC_BASE_URL to the externally reachable API base URL.
- Set CONQUMOVE_PUBLIC_CABLE_URL if cable must use a different public URL than <base_url>/cable.
- If CONQUMOVE_PUBLIC_CABLE_URL is not set, the API returns <public_base_url>/cable.

Recommended iOS environments:
- Debug -> local API
- Staging -> shared staging API
- Release -> production API

2. Register
POST /api/v1/auth/register
{
  "email": "runner@example.com",
  "password": "password123",
  "password_confirmation": "password123"
}

Response:
{
  "user": {
    "id": "uuid",
    "email": "runner@example.com"
  },
  "access_token": "opaque-token",
  "access_token_expires_at": "timestamp",
  "refresh_token": "opaque-token",
  "refresh_token_expires_at": "timestamp"
}

3. Login
POST /api/v1/auth/login
Body matches register without password_confirmation.

4. Refresh
POST /api/v1/auth/refresh
{
  "refresh_token": "opaque-refresh-token"
}

Refresh rotates the previous refresh token and returns a new access + refresh pair.

5. Authenticated API calls
Use header:
Authorization: Bearer <access_token>

6. Standard error response

All 401 / 403 / 422 / 429 responses use the same envelope:
{
  "error": {
    "code": "machine_readable_code",
    "message": "Human readable message",
    "details": { }
  },
  "request_id": "request-id"
}

Examples:
- 401 missing or expired access token -> code: unauthorized
- 401 login failure -> code: invalid_credentials
- 401 refresh failure -> code: invalid_refresh_token
- 403 admin-only endpoint -> code: forbidden
- 422 validation or missing params -> code: validation_error or unprocessable_entity
- 429 rate limiting -> code: rate_limited

429 responses also include:
- Retry-After header with seconds

8. Movement batch ingestion
POST /api/v1/movement/batch
Authorization: Bearer <access_token>
{
  "session_id": "session-uuid",
  "idempotency_key": "uuid-or-client-batch-id",
  "points": [
    {
      "lat": 41.015,
      "lng": 28.979,
      "timestamp": "2026-06-04T12:00:00Z",
      "speed": 5.2,
      "accuracy": 8.0,
      "source": "ios"
    }
  ]
}

Rules:
- timestamp must be ISO8601 UTC string
- idempotency_key must be unique per session and stable for retries
- retrying with the same session_id + idempotency_key + identical payload is safe
- retrying the same idempotency_key with a different payload is rejected
- source should remain "ios" unless another explicit mobile source is introduced

Response:
{
  "session_id": "session-uuid",
  "batch_uuid": "uuid-or-client-batch-id",
  "accepted": true,
  "points_received": 1
}

10. Nearby realtime subscription contract
GET /api/v1/realtime/subscriptions/nearby?lat=41.01&lng=29.02&radius=1

Response:
{
  "cable_url": "https://api.example.com/cable",
  "hex_ids": ["8928308280fffff"],
  "channels": {
    "territory_updates": {

13. Cable lifecycle expectations

iOS client should follow this sequence:
- Connect using current access token
- Subscribe to nearby channels returned by /realtime/subscriptions/nearby
- If HTTP requests start returning 401, refresh token pair first
- After a successful refresh, reconnect cable with the new access token
- Re-fetch nearby contract if the user location scope changed materially
- On reconnect, resubscribe using the latest known hex_ids

Backend expectations:
- access token can be passed via cable query param token
- expired / invalid cable token should be treated as unauthorized connection
- refresh does not hot-swap an existing cable socket; client should reconnect explicitly
